\chapter{Introduction}

\section{Purpose}
This Software Requirements Specification (SRS) defines the functional and non-functional
requirements of \textbf{GiftCompass}, a web-based system that recommends gifts by first
building a structured profile of the person who will receive the gift, and then matching
that profile against a catalogue of products available in Jeddah, Saudi Arabia, within a
budget set by the giver.

The document specifies:
\begin{itemize}
  \item the behaviour required of all twelve system modules listed in Section~\ref{sec:functions};
  \item the external interfaces through which users and other software interact with the system;
  \item the data the system processes, and the constraints on processing personal data;
  \item the non-functional qualities the system must exhibit;
  \item the criteria by which each requirement can later be verified.
\end{itemize}

\noindent The document does \emph{not} specify the internal design of the system, the choice
of algorithms beyond what is required for observable behaviour, the database schema, or the
test cases themselves. Those belong to the Software Design Document and the test
specification respectively.

\end{itemize}

\section{Product Scope}
\subsection*{In scope}
GiftCompass is a web application that:
\begin{itemize}
  \item collects the gift context from the giver: relationship to the recipient, occasion,
        budget in Saudi Riyals (SAR), and the time available before the occasion;
  \item collects information about the recipient through a short structured questionnaire,
        and optionally through a consent-based TikTok Gift Profile;
  \item constructs a \emph{Recipient Profile}: a structured set of weighted interests, each
        supported by evidence, together with dislikes and style preferences;
  \item retrieves candidate products from a curated catalogue of items available in Jeddah;
  \item applies constraint filters (budget, delivery time, age suitability, relationship
        appropriateness, stated dislikes) before ranking;
  \item ranks the surviving candidates and presents up to five recommendations;
  \item explains, in one or two sentences per recommendation, why each item was selected;
  \item allows the giver to refine the result set and to record feedback;
  \item links the giver to an external seller to complete the purchase.
\end{itemize}

\subsection*{Out of scope}
GiftCompass does not:
\begin{itemize}
  \item process payments, hold stock, arrange delivery, or handle returns --- the purchase is
        completed on the seller's own site;
  \item collect data about any person without that person's consent, or scrape any social
        media platform;
  \item provide social networking, messaging between users, or user-to-user gifting;
  \item guarantee that a recommended product is in stock or priced as displayed at the moment
        of purchase; the system reports catalogue data and links to the seller for
        confirmation;
  \item operate outside the Jeddah market in this version.
\end{itemize}

\subsection*{Development status}
This SRS specifies the complete intended system. A prototype covering the recommendation
pipeline has been implemented; the requirements in this document that are not yet
implemented are stated as requirements on the system to be delivered, not as descriptions of
existing behaviour. Section~\ref{sec:assumptions} distinguishes confirmed capability from
planned capability.

\chapter{Overall Description}

\section{Product Perspective}
GiftCompass is a new, self-contained web application. It is not a replacement for, nor a
component of, an existing system. It sits between the giver and the retail market: it does
not sell products, and it does not hold inventory. Its role is to reduce a large product
space to a small, justified set of suggestions, and then hand the user to a seller.

Architecturally the system is organised as a pipeline of independently replaceable modules:

\begin{center}
\small
\texttt{Gift context + recipient information} $\rightarrow$ \texttt{Recipient Profile}
$\rightarrow$ \texttt{candidate retrieval} $\rightarrow$ \texttt{constraint filtering}
$\rightarrow$ \texttt{ranking} $\rightarrow$ \texttt{explanation} $\rightarrow$
\texttt{results, refinement, feedback}
\end{center}

\noindent Two properties of this arrangement are requirements in themselves rather than
design preferences. First, constraint filtering occurs \emph{before} ranking (FR-29), so a
product that violates a stated constraint can never be ranked or displayed. Second, every
module communicates through a defined data contract (Section~\ref{sec:software-if}), so a
module may be replaced without altering the others.

\section{User Classes and Characteristics}
Three user classes are recognised. No further roles are introduced, because the system
neither sells products nor hosts recipient accounts.

\begin{description}[style=nextline,leftmargin=0pt]
  \item[UC-1 --- Gift giver (primary user)]
        An individual in Jeddah choosing a gift for another person. Assumed to be comfortable
        using a web application on a mobile device, to read Arabic or English, and to have no
        technical knowledge of the system. This class performs the entire main flow and is
        the actor for the majority of requirements.
  \item[UC-2 --- Gift recipient (consenting data subject)]
        The person the gift is for. This class does not use the recommendation features. Its
        only interaction is optional: opening a Gift Profile invitation, deciding what to
        share, reviewing the interests the system inferred, and approving, editing or
        declining. This class is the data subject for all recipient personal data and holds
        the rights specified in FR-62 to FR-68.
  \item[UC-3 --- Catalogue maintainer (project team role)]
        A member of the project team responsible for adding products, verifying prices and
        availability, and marking records as verified. This is an internal role exercised
        through project tooling rather than a public administrative interface.
\end{description}

\section{Operating Environment}
\begin{description}[style=nextline,leftmargin=0pt]
  \item[Client] A current desktop or mobile web browser supporting HTML5, CSS3 and
        JavaScript. The system is used predominantly on mobile devices and the interface is
        specified as mobile-first (UIR-02). No installation is required.
  \item[Server] A web application server exposing the application and its internal service
        endpoints over HTTPS. The prototype is developed on a JavaScript/TypeScript
        application framework; the deployment platform is not fixed by this specification.
  \item[Data storage] Persistent storage for the product catalogue, Recipient Profiles,
        consent records and feedback. A relational database is required; a relational
        database with vector-similarity support is the proposed candidate, but this
        specification does not mandate a product.
  \item[Recommendation components] The Recipient Profile Builder and the ranking components
        are required to behave as specified in Section~\ref{sec:fr}. The current prototype
        implements them deterministically; a language-model-based profile builder and a
        semantic retrieval component are planned substitutions behind the same interfaces
        (see Section~\ref{sec:assumptions}).
  \item[Network] The system requires an internet connection at both client and server. It is
        not specified to operate offline.
  \item[External services] Outbound links to seller websites. No inbound dependency on an
        external service is required for the core recommendation flow to function.
\end{description}

\section{Design and Implementation Constraints}
\begin{description}[style=nextline,leftmargin=0pt]
  \item[C-1 Project scope and duration] The system is developed by a student team within a
        single academic year. Requirements are scoped to what such a team can deliver and
        verify.
  \item[C-2 Platform access] The system shall not depend on access to social media data that
        the project cannot lawfully and reliably obtain. This constrains the TikTok module
        (Section~\ref{sec:tiktok-fr}).
  \item[C-3 Product data] Product information is curated by the project team. The system
        shall not present product data as live retail data unless that record has been
        verified (FR-24).
  \item[C-4 Legal] Processing of personal data shall be designed to support the obligations
        of the Saudi Personal Data Protection Law, in particular consent, purpose limitation,
        data minimisation and the rights of the data subject.
  \item[C-5 Language] All user-facing text shall be available in Arabic and English
        (UIR-01), and the system shall handle recipient information expressed in either
        language (FR-26).
  \item[C-6 Currency and market] All monetary values shall be expressed in SAR, and product
        availability shall be assessed for delivery to or collection in Jeddah.
  \item[C-7 Budget] The project operates without a commercial budget; the system shall be
        operable on free or low-cost hosting and shall not require paid data feeds.
  \item[C-8 Connectivity] The system requires internet connectivity and is not specified for
        offline operation.
\end{description}

\section{Assumptions and Dependencies}
\label{sec:assumptions}
This section separates what is confirmed from what is assumed. Requirements elsewhere in the
document are written so that no requirement depends on an unconfirmed item.

\subsection*{Confirmed}
\begin{itemize}
  \item The recommendation pipeline --- profile construction, retrieval, filtering, ranking
        and explanation --- has been implemented and exercised end to end in a prototype.
  \item A curated demonstration catalogue of Jeddah-market products exists, spanning multiple
        categories and budget bands, with prices in SAR.
  \item A controlled interest vocabulary shared by profiles and products exists, and is the
        join between the two.
  \item The questionnaire route operates without any external platform.
  \item Recipient data can be obtained lawfully only with the recipient's consent; no route
        that bypasses consent is available to the project.
\end{itemize}

\subsection*{Assumed, to be confirmed}
\begin{itemize}
  \item \textbf{A-1} A hosted language-model service will be available to the team at
        acceptable cost for profile construction and explanation generation. If it is not,
        the deterministic implementation satisfies the same requirements with reduced
        quality.
  \item \textbf{A-2} A multilingual sentence-embedding model can be integrated for semantic
        retrieval. If it is not, lexical retrieval satisfies FR-25 to FR-28.
  \item \textbf{A-3} Recipients who are invited will, in some proportion of cases, choose to
        create a Gift Profile. The system does not depend on this (FR-59).
  \item \textbf{A-4} Catalogue prices can be verified against seller listings at a cadence
        the team can sustain. FR-22 to FR-24 are written to make the verification state
        explicit rather than to assume freshness.
  \item \textbf{A-5} Users have a device and connection adequate for a standard responsive
        web application.
\end{itemize}

\subsection*{Dependencies}
\begin{itemize}
  \item Availability of the hosting platform and database service.
  \item Availability of seller websites for the outbound purchase link. A broken or changed
        seller link affects only the final step (ERR-06).
  \item For the optional TikTok route: the continued availability to the recipient of the
        platform's own user-data export function. No dependency on a platform API is
        specified.
\end{itemize}

\chapter{System Requirements}

\section{Functional Requirements}
\label{sec:fr}
Requirements are stated using \emph{shall}. Each requirement specifies one observable
behaviour and is written so that it can be verified by the method recorded in
Appendix~\ref{app:rtm}. Where a requirement refers to a configurable value, the value is
named as a system parameter rather than fixed in this document, so that it can be tuned
without amending the specification.

\subsection{User and Gift Request Requirements}
\begin{reqtable}{Gift request requirements (module M1)}
FR-01 & The system shall allow the giver to specify the relationship to the recipient by selecting exactly one value from a defined list that includes at least: friend, best friend, partner, mother, father, sister, brother, relative, colleague, classmate and other. \\
FR-02 & The system shall allow the giver to specify the occasion by selecting exactly one value from a defined list that includes at least: birthday, graduation, anniversary, wedding, achievement, thank you, Eid, new job and no specific occasion. \\
FR-03 & The system shall require the giver to specify a maximum budget in SAR, either by selecting a predefined band or by entering a numeric value, and shall not proceed to recommendation without it. \\
FR-04 & The system shall allow the giver to specify the number of days remaining before the occasion, and shall treat this value as a delivery constraint (FR-31). \\
FR-05 & The system shall validate that a budget entered directly is a positive number within a configured permitted range, and shall reject non-numeric, zero, negative and out-of-range values with an explanatory message (ERR-02). \\
FR-06 & The system shall retain the gift context (relationship, occasion, budget, days remaining) for the duration of the session so that it is reused on refinement without being re-entered (FR-48). \\
\end{reqtable}

\subsection{Recipient Questionnaire Requirements}
\begin{reqtable}{Questionnaire requirements (module M2)}
FR-07 & The system shall provide a structured questionnaire about the recipient consisting of no more than twelve questions, of which the majority shall be single- or multiple-choice rather than free text. \\
FR-08 & The questionnaire shall collect, at minimum: the recipient's interests, how they spend free time, their style or aesthetic preference, whether they prefer practical or sentimental gifts, and anything they would not want to receive. \\
FR-09 & The questionnaire shall not re-request the relationship, occasion or budget already captured by module M1. \\
FR-10 & The system shall accept a completed questionnaire in which optional questions are unanswered, and shall construct a Recipient Profile from the answers provided (FR-16). \\
FR-11 & The system shall record each questionnaire answer as an interest signal carrying its source and the date on which it was given, for use as evidence (FR-14). \\
\end{reqtable}

\subsection{Recipient Profile Requirements}
\begin{reqtable}{Recipient Profile requirements (module M3)}
FR-12 & The system shall construct a Recipient Profile consisting of weighted interests, dislikes, style attributes and, where stated, items the recipient already owns. \\
FR-13 & Each interest in the Recipient Profile shall be drawn from the system's controlled interest vocabulary, so that interests join directly to product attributes (FR-20). \\
FR-14 & Each interest shall carry at least one item of evidence recording the source, the signal type and the date. An interest without evidence shall not be added to the profile. \\
FR-15 & The system shall assign each interest a numeric weight computed from the strength and the recency of its supporting signals, such that repeated and recent evidence yields a higher weight than a single or older signal, and shall classify the weight into a strength band. \\
FR-16 & Where the available signals are insufficient to produce at least one interest, the system shall not fabricate an interest; it shall record the profile as incomplete and inform the giver (ERR-07). \\
FR-17 & Where a signal expresses a negative sentiment toward a topic, the system shall record that topic as a dislike and shall not record it as an interest. \\
FR-18 & The system shall not infer, derive or store any attribute relating to religion, health, political opinion, sexual orientation, ethnicity or financial status, irrespective of what the available signals would permit. \\
\end{reqtable}

\subsection{Product Catalogue Requirements}
\begin{reqtable}{Product catalogue requirements (module M4)}
FR-19 & The catalogue shall store, for each product: an identifier, a name in Arabic and English, a category, a price in SAR, an age range, the occasions it suits, the relationships it suits, delivery time in days, availability in Jeddah, and a seller reference. \\
FR-20 & Each product shall be annotated with one or more interest keys drawn from the same controlled vocabulary used by the Recipient Profile (FR-13). \\
FR-21 & Each product shall carry a numeric giftability attribute and a numeric social-appropriateness (embarrassment risk) attribute, for use in filtering and ranking (FR-34, FR-37). \\
FR-22 & Each product record shall carry a verification status of either \emph{verified} or \emph{unverified}, and, where verified, the date of verification. \\
FR-23 & The system shall support updating a product's price, availability and verification status without altering its identifier or its interest annotations. \\
FR-24 & The system shall exclude unverified product records from results presented to an end user when operating in a mode configured for end-user use, and shall label any unverified data shown in development or demonstration mode. \\
\end{reqtable}

\subsection{Gift Matching and Retrieval Requirements}
\begin{reqtable}{Matching and retrieval requirements (module M5)}
FR-25 & The system shall retrieve a bounded set of candidate products by comparing the Recipient Profile against product records, using both the shared interest vocabulary and textual similarity. \\
FR-26 & Retrieval shall operate on product and profile text expressed in Arabic or in English, and shall not require the two to be in the same language. \\
FR-27 & The number of candidates retrieved shall be a configurable system parameter, and retrieval shall be performed before any constraint filtering is applied. \\
FR-28 & Where retrieval returns no candidate, the system shall report that no match was found and shall offer the giver the refinement options defined in FR-47, rather than returning an empty page without explanation (ERR-03). \\
\end{reqtable}

\subsection{Filtering Requirements}
\begin{reqtable}{Filtering requirements (module M6)}
FR-29 & The system shall apply all constraint filters to the candidate set before ranking, so that no product violating a constraint is ranked or displayed. \\
FR-30 & The system shall exclude any product whose price in SAR exceeds the maximum budget specified by the giver. \\
FR-31 & The system shall exclude any product whose delivery time in days exceeds the days remaining before the occasion, where the giver has supplied that value. \\
FR-32 & The system shall exclude any product whose stated age range does not overlap the recipient's age range, where an age range is known. \\
FR-33 & The system shall exclude any product whose suitable-relationship list does not include the relationship specified by the giver. \\
FR-34 & The system shall exclude any product whose social-appropriateness attribute exceeds the threshold configured for the specified relationship, where a closer relationship permits a higher threshold than a professional one. \\
FR-35 & The system shall exclude any product annotated with an interest key recorded as a dislike in the Recipient Profile, and any product matching an item recorded as already owned. \\
\end{reqtable}

\subsection{Ranking and Scoring Requirements}
\begin{reqtable}{Ranking requirements (module M7)}
FR-36 & The system shall assign each surviving candidate a score computed from: the strength of its match to the Recipient Profile, its giftability, its fit to the stated budget, its novelty, and its social-appropriateness, with the relative weighting of these terms held as a configurable system parameter. \\
FR-37 & The scoring function shall treat higher social-appropriateness risk as reducing the score, and shall never rank such an item above an otherwise equivalent item of lower risk. \\
FR-38 & The system shall exclude from the result set any candidate whose match to the Recipient Profile falls below a configured relevance threshold, even where this reduces the number of results returned. \\
FR-39 & The system shall limit the number of results drawn from any single product category to a configurable maximum, so that the result set presents distinct alternatives rather than variants of one item. \\
FR-40 & Where a language model is used to re-order the ranked candidates, it shall be permitted only to reorder identifiers already present in the filtered candidate set; any identifier it returns that is not in that set shall be discarded, and any identifier it omits shall retain its position. \\
\end{reqtable}

\subsection{Recommendation Explanation Requirements}
\begin{reqtable}{Explanation requirements (module M8)}
FR-41 & The system shall present, with each recommendation, an explanation of no more than three sentences stating why the product was selected for this recipient. \\
FR-42 & Each explanation shall refer to at least one interest recorded in the Recipient Profile, and shall refer only to interests actually present in that profile. \\
FR-43 & Each explanation shall state the product price in SAR in relation to the budget the giver specified. \\
FR-44 & Explanations shall not display internal scores, weights, confidence values or model identifiers to the end user. \\
\end{reqtable}

\subsection{Results and Refinement Requirements}
\begin{reqtable}{Results and refinement requirements (module M9)}
FR-45 & The system shall present at most five recommendations per request, ordered by score. \\
FR-46 & Where fewer than five candidates satisfy the constraints and the relevance threshold, the system shall present only those candidates and shall state that fewer results were found; it shall not add candidates that fail the threshold in order to reach five. \\
FR-47 & The system shall provide refinement controls allowing the giver to request results that are, at minimum: cheaper, more expensive, more practical, more sentimental, more unusual, from a different category, or additional to those already shown. \\
FR-48 & On refinement the system shall reuse the existing Recipient Profile and gift context without requiring the giver to re-enter them. \\
FR-49 & Each recommendation shall display the product name, its price in SAR, its category, the seller, and a control that opens the seller's page for that product. \\
\end{reqtable}

\subsection{Feedback Requirements}
\begin{reqtable}{Feedback requirements (module M10)}
FR-50 & The system shall allow the giver to record a positive or negative judgement on each individual recommendation. \\
FR-51 & Where a negative judgement is recorded, the system shall allow the giver to select a reason from a defined list including at least: too expensive, wrong style, already owned, wrong category, and not personal enough. \\
FR-52 & The system shall store feedback with a reference to the recommendation and the request that produced it, so that recommendation quality can later be analysed (NFR-13). \\
\end{reqtable}

integration. Table~\ref{tab:tiktok-scope} distinguishes what the prototype demonstrates from

\begin{reqtable}{TikTok Gift Profile requirements (module M11)}

FR-54 & The system shall present the recipient, on opening the invitation, with an explanation of what information is requested, the purpose for which it will be used, and a clearly available option to decline. \\

\subsection{Security, Privacy and Consent Requirements}
\begin{reqtable}{Security, privacy and consent requirements (module M12)}
FR-62 & The system shall record, for every Recipient Profile, the party who provided the basis for processing, the purpose, the sources covered and the date. The record shall distinguish two cases: (a)~\emph{recipient-provided}, where the recipient supplied information about themselves and gave consent; and (b)~\emph{giver-provided}, where the giver supplied their own knowledge of the recipient through the questionnaire. The two cases shall be distinguishable for every profile. \\
FR-63 & The system shall refuse to use a Recipient Profile that does not carry a valid record under FR-62, and shall report the refusal rather than proceeding with recommendation. A profile marked \emph{recipient-provided} shall additionally be refused where the recipient has not completed the approval step required by FR-58. \\
FR-64 & The system shall process personal data only for the purpose of producing gift recommendations, and shall provide no function that uses it for another purpose. \\
FR-65 & The system shall collect only those data items required by the modules specified in this document, and shall provide no function that requests unrelated personal information. \\
FR-66 & The system shall assign each Recipient Profile a retention expiry, shall not use a profile after its expiry, and shall delete expired profiles. The retention period shall be a configurable system parameter set by the project team. \\
FR-67 & The system shall allow the recipient to request deletion of their Recipient Profile, and shall delete it together with its evidence records on such a request. \\
FR-68 & The system shall present its consent and privacy information in both Arabic and English (UIR-01). \\
\end{reqtable}

\noindent\textbf{Note on the two processing bases.} The questionnaire route processes the
giver's own description of someone they know, which is the minimum information needed to
produce a recommendation and is supplied by the person making the request. The Gift Profile
route processes information originating from the recipient, and is therefore conditional on
that recipient's consent and explicit approval (FR-55, FR-58). The system keeps the two cases
distinguishable (FR-62) so that the correct rules can be applied to each, and so that a
deletion request can be satisfied in either case (FR-67). This document states system
requirements intended to support the obligations described in Section~\ref{sec:security}; it
does not itself determine the legal basis for processing, which is assessed separately by the
project team.

\chapter{System Features}
\label{sec:features}
\label{ch:features}
Each feature below is described with its purpose, actors, preconditions, flows, governing
requirements, inputs, outputs and constraints. Feature identifiers SF-1 to SF-12 are used in
the traceability matrix (Appendix~\ref{app:rtm}).

\section{SF-1 --- Gift Request}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] Captures the context of the gift: who it is for, why, how much may be spent and by when.
\item[Purpose] Establishes the constraints that all later filtering and ranking must respect, before any product is considered.
\item[Actors] Gift giver (UC-1).
\item[Preconditions] The user has opened the application. No account is required.
\item[Main flow] (1)~The user starts a gift request. (2)~The user selects the relationship. (3)~The user selects the occasion. (4)~The user sets a budget in SAR. (5)~The user optionally states the days remaining before the occasion. (6)~The system stores the gift context and proceeds to recipient information (SF-2 or SF-4).
\item[Alternative and exception flows] (a)~The user enters an invalid budget: ERR-02 applies and the step is repeated. (b)~The user returns to an earlier step: UIR-03 requires previously entered values to be preserved. (c)~The user abandons the flow: no personal data has been collected at this point.
\item[Requirements] FR-01--FR-06, UIR-03, ERR-01, ERR-02.
\item[Inputs] Relationship, occasion, budget (SAR), days remaining.
\item[Outputs] A stored gift context for the session.
\item[Constraints] The budget is mandatory (FR-03). Exactly one relationship and one occasion may be selected (FR-01, FR-02).
\end{description}

\section{SF-2 --- Recipient Questionnaire}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] A short structured questionnaire about the recipient, answered by the giver.
\item[Purpose] Provides the always-available route to recipient information, requiring no participation by the recipient and no external platform.
\item[Actors] Gift giver (UC-1).
\item[Preconditions] A gift context exists (SF-1).
\item[Main flow] (1)~The system presents the questions. (2)~The user answers. (3)~The system records each answer as an interest signal with source and date. (4)~The system passes the signals to the Recipient Profile Builder (SF-3).
\item[Alternative and exception flows] (a)~The user skips optional questions: FR-10 requires the profile to be built from what was given. (b)~Too few answers to yield any interest: ERR-07 applies and the user is invited to add more detail. (c)~The user has also completed SF-4: both signal sets feed the same profile (FR-60).
\item[Requirements] FR-07--FR-11, UIR-04, ERR-07.
\item[Inputs] Answers about interests, free time, style, practical or sentimental preference, and anything unwanted.
\item[Outputs] A set of interest signals.
\item[Constraints] At most twelve questions, mostly closed-form (FR-07). No re-asking of relationship, occasion or budget (FR-09).
\end{description}

\section{SF-3 --- Recipient Profile Builder}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] Converts interest signals, from whatever source, into a single structured Recipient Profile.
\item[Purpose] Produces one profile format for the whole system, so that the rest of the pipeline is independent of how the information was collected.
\item[Actors] System (invoked after SF-2 or SF-4).
\item[Preconditions] At least one interest signal exists, with a consent record where the signal came from the recipient.
\item[Main flow] (1)~The system maps each signal to the controlled interest vocabulary. (2)~It determines sentiment, routing negative mentions to dislikes. (3)~It computes a weight per interest from signal strength and recency. (4)~It classifies each weight into a strength band. (5)~It attaches the supporting evidence to each interest. (6)~It records the profile with a completeness indicator and an expiry.
\item[Alternative and exception flows] (a)~No signal maps to the vocabulary: FR-16 requires the profile to be recorded as incomplete, with no invented interest. (b)~A topic appears with both positive and negative sentiment: FR-17 gives precedence to the dislike, and the topic is excluded from recommendation. (c)~A signal would imply a prohibited attribute: FR-18 requires it to be discarded.
\item[Requirements] FR-12--FR-18, FR-60, DR-01--DR-03, DR-06.
\item[Inputs] Interest signals with source, type and date.
\item[Outputs] A Recipient Profile: weighted interests with evidence, dislikes, style attributes, completeness, expiry.
\item[Constraints] No interest without evidence (FR-14). No prohibited attribute, under any circumstances (FR-18).
\end{description}

\section{SF-4 --- TikTok Personalisation (Gift Profile)}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] An optional route in which the recipient supplies their own TikTok-related information, reviews what the system inferred, and approves it.
\item[Purpose] Enriches the Recipient Profile with interest signals the giver may not know, without the system obtaining data about anyone without their action and consent.
\item[Actors] Gift giver (UC-1) creates the invitation; gift recipient (UC-2) decides and supplies.
\item[Preconditions] A gift request exists. The recipient has received the invitation link.
\item[Main flow] (1)~The giver generates an invitation link. (2)~The recipient opens it and is shown the purpose and the decline option. (3)~The recipient consents. (4)~The recipient supplies their information. (5)~The system extracts only signals mapping to the interest vocabulary. (6)~The system presents the inferred interests for review. (7)~The recipient removes any entry and approves. (8)~The system builds the profile (SF-3) and deletes the source material.
\item[Alternative and exception flows] (a)~The recipient declines or does not respond: FR-59 requires the questionnaire route to proceed. (b)~The information cannot be processed: ERR-08 applies, nothing is retained, and the questionnaire route proceeds. (c)~The recipient removes every inferred interest: the profile is treated as having no signals from this source. (d)~The recipient later requests deletion: FR-67 applies.
\item[Requirements] FR-53--FR-61, FR-62--FR-68, SEC-06, SEC-08, ERR-08, UIR-05.
\item[Inputs] Recipient consent; recipient-supplied information.
\item[Outputs] An approved set of interests contributing to the Recipient Profile; a consent record; confirmation that source material was deleted.
\item[Constraints] No data is obtained about a recipient without that recipient's own action (FR-55). Nothing is stored before approval (FR-58). The system remains fully functional if this feature is never used (FR-59).
\end{description}

\section{SF-5 --- Product Catalogue}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] The curated set of products available in the Jeddah market, with the attributes required for matching, filtering and ranking.
\item[Purpose] Provides the candidate space. Without accurate attributes the rest of the pipeline cannot enforce its constraints.
\item[Actors] Catalogue maintainer (UC-3); system (read access).
\item[Preconditions] None for reading. Write access is restricted to the maintainer role.
\item[Main flow] (1)~The maintainer adds or edits a product record. (2)~The maintainer supplies interest keys from the controlled vocabulary. (3)~The maintainer verifies price and availability against the seller. (4)~The maintainer marks the record verified with a date. (5)~The record becomes eligible for end-user results.
\item[Alternative and exception flows] (a)~A record is unverified: FR-24 excludes it from end-user results. (b)~A price changes: ERR-05 governs what is displayed. (c)~A product becomes unavailable: ERR-04 omits it from results.
\item[Requirements] FR-19--FR-24, DR-07, ERR-04, ERR-05.
\item[Inputs] Product attributes; verification outcome.
\item[Outputs] Catalogue records eligible for retrieval.
\item[Constraints] Prices in SAR (C-6). Availability assessed for Jeddah. No personal data in the catalogue (DR-07).
\end{description}

\section{SF-6 --- Gift Retrieval and Matching}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] Selects a bounded candidate set from the catalogue on the basis of the Recipient Profile.
\item[Purpose] Reduces the catalogue to a set small enough to filter and rank, without discarding relevant products.
\item[Actors] System.
\item[Preconditions] A Recipient Profile exists and carries valid consent (FR-63).
\item[Main flow] (1)~The system forms a query from the profile's interests, weighted by strength. (2)~It compares the query against product records by shared interest key and by textual similarity. (3)~It returns the highest-scoring candidates up to the configured limit.
\item[Alternative and exception flows] (a)~No candidate is returned: FR-28 and ERR-03 apply. (b)~The profile is in Arabic and products in English, or the reverse: FR-26 requires retrieval to operate across both.
\item[Requirements] FR-25--FR-28, FR-63.
\item[Inputs] Recipient Profile; catalogue.
\item[Outputs] An ordered candidate set.
\item[Constraints] Retrieval precedes filtering (FR-27).
\end{description}

\section{SF-7 --- Filtering}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] Removes candidates that violate a stated constraint.
\item[Purpose] Guarantees that no displayed recommendation breaches the budget, the timing, or the appropriateness of the relationship, regardless of how well it matches the profile.
\item[Actors] System.
\item[Preconditions] A candidate set exists; a gift context exists.
\item[Main flow] (1)~Remove candidates above budget. (2)~Remove candidates that cannot arrive in time. (3)~Remove candidates outside the recipient's age range. (4)~Remove candidates not suitable for the relationship. (5)~Remove candidates above the social-appropriateness threshold for that relationship. (6)~Remove candidates matching a dislike or an item already owned. (7)~Pass the remainder to ranking.
\item[Alternative and exception flows] (a)~All candidates are removed: ERR-03 applies, naming the constraint responsible and offering a relaxation. (b)~No age range is known: the age filter is not applied. (c)~No delivery deadline was given: the timing filter is not applied.
\item[Requirements] FR-29--FR-35, ERR-03.
\item[Inputs] Candidate set; gift context; Recipient Profile dislikes.
\item[Outputs] A filtered candidate set, with a record of how many were removed by each constraint.
\item[Constraints] Filtering is applied before ranking and is not overridable by score (FR-29).
\end{description}

\section{SF-8 --- Ranking and Scoring}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] Orders the filtered candidates and enforces variety and a minimum relevance.
\item[Purpose] Determines which of the acceptable products are presented, and in what order.
\item[Actors] System.
\item[Preconditions] A filtered candidate set exists.
\item[Main flow] (1)~Score each candidate on interest match, giftability, budget fit, novelty and social-appropriateness. (2)~Discard candidates below the relevance threshold. (3)~Apply the per-category limit. (4)~Order by score. (5)~Optionally re-order the leading candidates using a language model, constrained to the existing set. (6)~Pass at most five to presentation.
\item[Alternative and exception flows] (a)~Fewer than five candidates survive: FR-46 requires the shorter list to be presented as such. (b)~The model re-ordering returns an unknown identifier: FR-40 requires it to be discarded. (c)~The model service is unavailable: ERR-09 requires the deterministic order to stand.
\item[Requirements] FR-36--FR-40, FR-45, FR-46, ERR-09.
\item[Inputs] Filtered candidates; Recipient Profile; gift context.
\item[Outputs] An ordered result set of at most five items with score components retained for analysis.
\item[Constraints] A model may reorder but never introduce a candidate (FR-40). The list is never padded to reach five (FR-46).
\end{description}

\section{SF-9 --- Recommendation Explanation}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] Produces a short statement of why each recommendation was selected.
\item[Purpose] Allows the giver to judge the suggestion rather than accept it on trust; addresses UN-4.
\item[Actors] System.
\item[Preconditions] A ranked result set exists.
\item[Main flow] (1)~For each recommendation, identify the interest that drove the match. (2)~Compose a statement of at most three sentences referring to that interest and to the price in relation to the budget. (3)~Present it with the recommendation.
\item[Alternative and exception flows] (a)~No single interest dominates: the explanation refers to the general style recorded in the profile. (b)~Explanation generation fails: ERR-09 applies and the recommendation is shown with its attributes, without a generated sentence.
\item[Requirements] FR-41--FR-44, UIR-06.
\item[Inputs] Recommendation; Recipient Profile; gift context.
\item[Outputs] Explanation text in the user's selected language.
\item[Constraints] Only interests present in the profile may be cited (FR-42). No internal scores are shown (FR-44).
\end{description}

\section{SF-10 --- Results and Refinement}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] Presents the recommendations and allows the giver to adjust them without restarting.
\item[Purpose] Converts a single ranked list into a short, directed search; addresses UN-2.
\item[Actors] Gift giver (UC-1).
\item[Preconditions] A result set exists.
\item[Main flow] (1)~The system displays up to five recommendations with explanations. (2)~The user may open a seller page for any item. (3)~The user may select a refinement. (4)~The system re-runs retrieval, filtering and ranking with the adjusted parameter, reusing the existing profile and context. (5)~The revised results are displayed.
\item[Alternative and exception flows] (a)~A refinement yields no result: ERR-03 applies and the previous results remain available. (b)~A seller link fails: ERR-06 applies. (c)~The user refines repeatedly: each refinement is applied to the original profile, not cumulatively, unless the user states otherwise.
\item[Requirements] FR-45--FR-49, UIR-06, UIR-07, ERR-03, ERR-06.
\item[Inputs] Result set; refinement selection.
\item[Outputs] A displayed or revised result set; an outbound link to the seller.
\item[Constraints] The profile and gift context are never re-requested on refinement (FR-48).
\end{description}

\section{SF-11 --- Feedback}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] Records the giver's judgement of individual recommendations.
\item[Purpose] Provides the evidence base for assessing and improving recommendation quality.
\item[Actors] Gift giver (UC-1).
\item[Preconditions] A recommendation has been displayed.
\item[Main flow] (1)~The user records a positive or negative judgement. (2)~Where negative, the user selects a reason. (3)~The system stores the judgement against the recommendation and request.
\item[Alternative and exception flows] (a)~The user gives no feedback: this is the normal case and no behaviour depends on it. (b)~The user changes a judgement: the latest value is retained.
\item[Requirements] FR-50--FR-52, DR-08, NFR-13.
\item[Inputs] Judgement; optional reason code.
\item[Outputs] A stored feedback record.
\item[Constraints] Feedback is stored against a recommendation, not against a person (DR-08).
\end{description}

\section{SF-12 --- Security, Privacy and Consent}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Description] The cross-cutting controls governing consent, minimisation, retention, deletion and protection of data.
\item[Purpose] Ensures personal data is processed only with consent and only for the stated purpose; addresses UN-7 and constraint C-4.
\item[Actors] Gift recipient (UC-2) as data subject; system as enforcement point.
\item[Preconditions] Applies to every operation on a Recipient Profile.
\item[Main flow] (1)~Consent is recorded when given (FR-62). (2)~The recommendation pipeline checks for valid consent before use (FR-63). (3)~Only data required by a requirement is collected (FR-65). (4)~Source material is deleted after profile construction (FR-61). (5)~Profiles expire and are deleted (FR-66). (6)~A deletion request is honoured (FR-67).
\item[Alternative and exception flows] (a)~Consent is absent or invalid: FR-63 requires the pipeline to refuse and report, not to proceed. (b)~A profile has expired: FR-66 forbids its use. (c)~A deletion request arrives while a request is in progress: deletion takes precedence and the recommendation request is terminated.
\item[Requirements] FR-62--FR-68, SEC-01--SEC-10, DR-01--DR-08, NFR-05, NFR-06.
\item[Inputs] Consent decisions; deletion requests.
\item[Outputs] Consent records; deletion confirmations; security event log entries without personal data.
\item[Constraints] The system provides no function that processes recipient data without a consent record (FR-63); this is a hard behaviour, not a configurable one.
\end{description}

The system shall return a complete set of recommendations, including explanations, within

The system shall be available during scheduled demonstration and evaluation periods. Planned

for a project prototype. \\

The system shall hold no personal data item that is not required by a stated requirement, and
shall hold no prohibited attribute. Verification is by inspection of the stored data model
against Table~\ref{tab:entities} and by an automated check that no prohibited attribute
appears in a stored profile. \\
NFR-07 & Maintainability &
Each pipeline module shall be replaceable without modification to the others, as required by
SIR-03. Verification is by demonstration: substituting one module implementation for another
shall require no change outside that module. \\
NFR-08 & Scalability &
The system shall maintain the NFR-01 response target with a catalogue of at least 1{,}000
products and at least 5 concurrent users. Beyond this, scalability is not specified for the
prototype. \\
NFR-09 & Compatibility &
The system shall function correctly in the current release, and the immediately preceding
release, of at least three major browsers, on both desktop and mobile. Verification is by
executing the main flow on each. \\
NFR-10 & Accessibility &
Interactive elements shall be operable by keyboard alone, every form control shall have an
associated label, and text shall meet a contrast ratio of at least 4.5:1. Verification is by
automated accessibility check plus manual keyboard traversal of the main flow. \\
NFR-11 & Localisation &
All user-facing text shall be present in Arabic and English with no untranslated string in
either, layout shall adapt to right-to-left presentation for Arabic, and all monetary values
shall display in SAR. Verification is by inspection of both language builds of every screen. \\
NFR-12 & Data integrity &
Every Recipient Profile and product record shall validate against its published schema before
being stored or used; an instance failing validation shall be rejected rather than stored
partially. Verification is by test with deliberately malformed instances. \\
NFR-13 & Recommendation quality &
Recommendation quality shall be evaluated against a defined baseline in which only
questionnaire input is used. For a set of test recipients, independent assessors shall rate
each recommendation for relevance on a three-point scale and record whether it would be
socially inappropriate. The target is a mean relevance of at least 1.5 of 2.0 and no
recommendation rated socially inappropriate. Where the target is not met, the result shall be
reported as measured rather than adjusted. \\

\noindent\textbf{Note on NFR-13.} This requirement specifies how quality is to be measured and
what target is being aimed at. It does not assert that the system will achieve the target, and
no requirement in this document claims that a recommendation will be correct for any
particular recipient.

\section{Verification Methods}
Every requirement is assigned one of four verification methods.

\begin{table}[htbp]
\centering\small
\caption{Verification methods}\label{tab:methods}
\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
\textbf{Method} & \textbf{Definition} \\ \midrule
T --- Test & The requirement is checked by executing the system with defined inputs and comparing the output against an expected result. Applies to most functional requirements. \\
I --- Inspection & The requirement is checked by examining the implementation, the data model or the interface without executing it. Applies to structural and data-protection requirements. \\
D --- Demonstration & The requirement is checked by operating the system and observing the behaviour, without instrumented measurement. Applies to flows and user interface behaviour. \\
A --- Analysis & The requirement is checked by measurement over a sample and evaluation of the result. Applies to performance and quality requirements. \\
\bottomrule
\end{tabularx}
\end{table}

\section{Traceability Approach}
Traceability runs in both directions:
\begin{itemize}
  \item \textbf{Forward:} each user need in Table~\ref{tab:needs} maps to one or more
        functional requirements, each functional requirement is realised by exactly one system
        feature, and each feature carries a verification method.
  \item \textbf{Backward:} every functional requirement traces to at least one user need. A
        requirement that traces to no need is removed at review; a need with no requirement
        indicates a gap in the specification.
\end{itemize}

\noindent Appendix~\ref{app:rtm} records the matrix. When a requirement changes after
baselining, the change is recorded in the Document Control table, the matrix row is updated,
and the associated verification activity is repeated.

\chapter{Glossary}
\label{app:glossary}
\begin{description}[style=nextline,leftmargin=0pt]
\item[Artificial intelligence (AI)] In this document, software components that derive structured information from unstructured input, or that rank alternatives using a learned or computed model, rather than by a fixed rule stated by the developer.
\item[Candidate retrieval] The step that selects a bounded subset of the catalogue for further processing, before any constraint is applied.
\item[Controlled interest vocabulary] The fixed set of interest keys used by both Recipient Profiles and product records, which makes matching a direct join rather than a text comparison.
\item[Evidence] The record of which signal, from which source and on which date, supports a given interest in a Recipient Profile.
\item[Filtering] The removal of candidates that violate a stated constraint. Distinct from ranking: filtering is absolute, ranking is relative.
\item[Giftability] An attribute expressing how well an interest or product works as a gift, as distinct from how well it matches the recipient.
\item[Gift context] The relationship, occasion, budget and timing supplied by the giver.
\item[Gift Profile] The consent-based route by which a recipient supplies their own information to enrich their Recipient Profile.
\item[Interest signal] A single observation suggesting an interest, carrying a source, a type and a date.
\item[Ranking] The ordering of candidates that have already satisfied every constraint.
\item[Recipient Profile] The structured record of a recipient's weighted interests, dislikes and style attributes, with evidence for each interest.
\item[Recommendation engine] The combination of the retrieval, filtering and ranking modules.
\item[Signal strength] The relative evidential weight of a signal type; a deliberate action is treated as stronger evidence than a passive one.
\item[Social-appropriateness (embarrassment risk)] An attribute expressing the risk that a product would be awkward given the stated relationship.
\item[TikTok personalisation] The optional enrichment of a Recipient Profile from information the recipient supplies themselves, with consent.
\end{description}
